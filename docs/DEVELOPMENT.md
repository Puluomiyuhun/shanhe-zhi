# 开发与跨电脑交接

## 最短恢复流程

```sh
git clone https://github.com/Puluomiyuhun/shanhe-zhi.git
cd shanhe-zhi
python -m http.server 8080 --directory dist
```

Windows 可把 `python` 换成 `py`。打开 `http://localhost:8080/`，应自动到 `/lab/`，显示 35 城／9 势力的三维地图。若仍见二维舆图，检查当前分支、`git pull` 结果、服务目录和 URL；再检查缓存，不能首先假定最新版代码没提交。

项目无需 npm install，无构建步骤。Three.js 已在 `dist/lab/vendor/`。需要 WebGL 2 与硬件加速。HTML 直接通过 `file:` 打开不能正常运行 ES 模块；默认页会显示 HTTP 启动说明。

## 状态与时间约束

`world.unit.cell` 是最后结算的格心，`unit.path` 是尚未到达的格子列表。可见位置可能在两格之间，不要把可见位置强制绑定为逻辑格心。`marchMotion` 保存段内进度，主循环仅在 running 时传入时间。人工单步明确结束下一格。

主角到格调用 `world.step()`，处理格子归属、步数、补给与士气；只有地盘改变才重建染色边界。`orderRoute` 是独立于 `clearPreview()` 的层。取消和重置时要同时处理军令、运动段、路线资源。

AI 每个行动者有路径、进度、等待、阶段和目标。巡防、出征返军、周游采用不同规则；不接入战斗就不要擅自改变兵力／城池归属。主角和 AI 使用同一主循环的暂停开关及时间增量，后台恢复不补跑大量时间。

城市侧栏的路线缓存假设当前 world 内地形与通行成本固定，归属不会改变通行成本。未来若添加道路建设、动态障碍或外交禁行，必须增加缓存失效机制。

旧二维存档在浏览器 localStorage（`shanhe-save-v2`，兼容 v1）；Git 同步不包含玩家存档，换电脑也不会自动带过去。三维目前无存档。

## 验证

需要 Node.js 22 或更新版本。按涉及范围选择；大幅修改世界或时间逻辑时可完整运行：

```sh
node verify-expansion.mjs
node verify-factions.mjs
node verify-actors.mjs
node verify-density.mjs
node verify-order-route.mjs
node verify-march-motion.mjs
```

| 脚本 | 重点 |
|---|---|
| expansion | 全格拾取、渡桥路线、补给封锁与恢复 |
| factions | 城市唯一、在界内、归属有效、全部可达；35 城／9 势力断言随有意扩容更新 |
| actors | 五分钟行为循环、相邻格移动、无兵周游、返军、无意外占地、120 角度投影 |
| density | 地图构造、高度采样、各城寻路耗时；输出观察值，不是跨设备性能门槛 |
| order-route | 路径随行程缩短、目标稳定、抵达取消清理、释放几何 |
| march-motion | 每帧连续位置、暂停、时间切分一致、改道无跳变、取消、手动单步 |

浏览器回归建议：根入口 → 左键城市侧栏 → 右键新野立即移动 → 路线与目标可见 → 空格暂停恢复 → 右拖旋转不误下军令 → 远景城市保留标记 → 驻城主标恢复 → AI 动向 → 重置。改 UI 还需看实际画面和控制台；Node 测试不替代视觉验收。

## 性能认识

2026-09-23 原开发机内置浏览器，1280×720、默认画质：35 城与六 AI 的近／远景约 60 FPS，P95 16.8 ms；部分连续 600 帧样本没有超过 33.4 ms 的慢帧。远景 16 次绘制调用、约 205 万三角面；建图约 3.3～3.6 秒；单次较远寻路约 18～19 ms。

这些是当时设备与场景的观测，不是最低配置承诺。未测 4K、低配手机、全国地形或几百部队。60 FPS 受刷新率限制，不能直接推算剩余 GPU 性能。详情见根目录城池密度记录。

已做：静态建筑合批、地形走廊预计算与范围排除、名牌碰撞收缩、城市路线缓存、己方地块移动跳过无变化的地盘重建。

仍需关注：大地形始终使用细网格；寻路在主线程且 open 集合扫描；动态占地仍可能更新大缓冲／重建边界；大量 DOM 名牌及同时决策尚未压测。全国扩容前优先验证分块与 LOD、路径调度／Worker、局部更新，而非仅减少城池数量。

## Git 与部署

GitHub 是可在新电脑直接启动的静态项目。此前开发环境另有 Sites 发布 checkout，与 GitHub 快照并非同一个目录；那是旧机器的工作方式，不是新电脑必须复制的架构。

当前在线试玩地址：
`https://sanguo-shanhe-chronicle-0918.cheery-tern-6088.chatgpt.site/`

Sites 的 `.openai/` 配置未进入 GitHub。新电脑若只 clone 仓库，应先本地运行；需要发布到已有站点时，通过已授权的 Sites 工具打开该站点、同步正确源码并保留现有访问权限。不要凭空创建同名新站点、假定 Git push 自动部署，或从历史聊天寻找凭据。

旧 Windows 环境的 Sites 辅助打包曾因缺 Bash 失败，源代码推送可能已先完成；这是机器相关问题。若再遇到，先检查实际提交和工具结果，按当前工具文档打包，不要盲目重复推送。不要把这条经验当成绕过当前发布流程的指令。

提交前看 diff，保留素材署名，不添加生成的压缩包、日志、缓存、凭据。仅在用户授权范围内推送；文档修改不需要重新发布游戏。

## 军令与情报 UI

最新样式覆盖为 `dist/lab/interface.css`；悬停浮层由 `map-peek.js` 管理，不能改旗牌尺寸。`intelligence.js` 城市路线缓存需随世界、玩家格子与封锁状态失效。修改菜单时保留 citiesInfo / unitsInfo 等侧栏依赖的 ID；顶部列表与地图对象侧栏分工不同。

## 驻城名录与缩放性能

`officer-data.js` 扩充角色，`portrait-data.js` 与 assets/portraits 管理 30 张对应头像。驻城查询使用 `officersInCity`，动态武将按实时位置计算，不能又显示在老驻地。没有头像时保留姓名章。城市侧栏不要每 400 ms 无条件重建人物 DOM。

`terrain-picking.js` 的 100 个分区共用原始顶点，不能加入 scene；未来变更地形顶点后需要同步包围盒。`performance-probe.js` 提供固定路线的 18 秒缩放测量；结果是本机观测。回归追加 `node verify-roster.mjs`、`node verify-terrain-picking.mjs`。后者较慢，因为同时测原始全网格作等价性和性能对照。

## 2026-09-24 兵站与地图平移

军营扩展为兵站（内部 kind=camp），每城最多一座，沿用现有工役队、建设成本和全局军队上限。兵站每旬从所属城调粮最多180、保留城粮1200，容量1800；不生成免费粮食。敌军6距离内停止整备和调粮。安全时完整度每旬恢复2。

AI出征可经顺路兵站集结2旬；缺粮或低士气可去22距离内己方兵站休整5旬，14旬冷却，不凭空恢复兵员。每旬至多补240粮、恢复10士气，然后恢复原军令。AI优先评估附近敌国兵站，袭击沿真实路径执行；附近敌军数量提高威胁评分，守方沿用迎击逻辑。毁站焚毁粮储，24旬内不重建。停战、易主、敌军逼近会取消整备或袭击。主角可左键兵站看侧栏，点击集结或右键前往；停驻且推进时每旬消耗60粮恢复8士气。主角仍不参加AI自动战斗，不可把休整解释成补充兵员。

减法：无建筑等级树、运输队、全地图实时补给网络、独立驻站军队槽；兵站结算按旬，不在渲染帧扫描。地图模型仅设施变化时按材质合批。复用既有农商军三类设施。

平移优化：输入合并到动画帧，释放鼠标时补最后位移；投影只更新根节点矩阵，避免额外递归整棵场景树；隐藏地理标签跳过投影；AI旗牌文字/颜色/状态只在变化时写DOM；标签使用translate合成提示；取消右侧栏对移动地图的实时背景模糊。没有通过降低地图规模解决问题。

新增 verify-depots.mjs：施工、有限粮储、军队休整恢复原目标、重复命令防护、主角恢复、敌军阻断、袭击摧毁及重建冷却。两剧本 verify-campaign.mjs / verify-evolution.mjs 各500旬通过，原有兵力守恒仍成立。操作说明→样区说明增加18秒平移评测；测的是浏览器镜头往返，不等价于不同显卡上的保证帧率。原 /lab/ 保留不变。
